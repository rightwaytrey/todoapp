# TaskMaster — design decisions

*2026-09-02. Written by the planner before any code. Short on purpose: this is
the list of decisions, each with the reason, so a later session does not
re-derive them.*

## What this is

The phone front-end for the tasks that already live in Taskwarrior on the home
server. It replaces **Taskchamp** (the iOS Taskwarrior app synced through the
TaskChampion sync server), which the user is done with for two reasons:

- **Sync lag.** Taskchamp is pull-only; its widget reads a cache that only
  updates when the app is foregrounded, and it never registered for Background
  App Refresh. A task added on the desktop reaches the phone whenever the phone
  gets around to it.
- **Filter confusion.** Taskchamp's filters are premium-gated, its grammar is a
  tiny custom one, and its synthetic date tags (`+TODAY`, `+OVERDUE`) are broken
  on the user's build. The morning list only works because a 5-minute timer on
  the desktop paints real `+today`/`+overdue`/`+due` tags onto tasks so the phone
  can exact-match them.

The user's words: *"none of the sync lag, less filter confusion. Just simple
record tasks on phone, complete them."*

## D1 — Taskwarrior stays the store; the app talks to an API, not a sync

There is no sync at all. The phone calls a small HTTP API on the home server
that shells out to `task`. The server is the single source of truth; the phone keeps a
localStorage cache so it renders instantly and can capture offline, and replays
queued writes when it is back on the tailnet.

**Why not a new database:** everything downstream of Taskwarrior keeps working
untouched — `pa roundup`/`digest`/`remind` (Pushover), the `+claude` queue that
dispatches tasks to Claude sessions, the daily nags, the Scriptable home-screen
widget (fed by `/var/www/dash/todos/data.json`, regenerated by `pa retag` on
every task change through the `on-add`/`on-modify` hooks). Swapping the store
would have re-implemented all of that for no gain on the two stated problems.

**Why shell out to `task` instead of reading the SQLite file:** the CLI is the
supported interface; it runs the hooks (which is what keeps the widget live),
maintains urgency, and expands recurrence. Verified on this box 2026-09-02
(Taskwarrior 3.4.2): `task rc.verbose=new-uuid add … -- <text>` prints the new
uuid and keeps `due:`/`project:` inside the text literal; `task <uuid> done`,
`modify status:pending` (un-complete), `modify due:` (clear), `annotate`,
`delete` all behave; `export` on the whole DB takes ~10 ms.

Taskchamp keeps working in parallel during the transition — the API's writes
still flow to the sync server through `pa-pushnow` — so nothing has to be
uninstalled on day one.

## D2 — No filters. One list, grouped.

The Tasks screen shows **every pending task**, grouped: Overdue, Today,
Upcoming (by due date), No date. Nothing is hidden by a filter, so nothing has to
be tagged to appear. Done is a second tab (last 30 days, tap to un-complete).
That is the entire information architecture. Projects, priority and tags are
shown on the row and edited in the detail sheet; they are never a gate on
visibility.

## D3 — Dates keep the `pa` date-vs-time rule

A due with no time is date-only (`due:2026-09-05` → local midnight): it shows in
the morning digest and never pings. A due with a clock time
(`due:2026-09-05T14:30`) pings via `pa remind` when it comes due. The API
exposes `due` as a local wall-clock string in exactly those two shapes so the
client never has to reason about UTC, and the detail sheet says which of the two
you are setting.

## D4 — Reach over the tailnet, plain HTTP, no new ports on the router

The phone is already on the tailnet; Home Assistant and the old Taskchamp sync
both work that way. The API listens on `:8101`, refuses any client that is not
loopback or in Tailscale's `100.64.0.0/10`, and the app's default server URL is
the server's MagicDNS name on port 8101. WireGuard already encrypts the path, so
this is HTTP over the tailnet, not HTTP over the internet; `Info.plist` carries
a scoped ATS exception for that one tailnet domain and nothing else. An optional
bearer token (`TASKMASTER_TOKEN`) is there for defence in depth.

**The host name is not in this repo.** It is the server's MagicDNS name (the
`TASKMASTER_API_BASE` secret) and the tailnet domain it sits in (the
`TASKMASTER_ATS_DOMAIN` secret), stamped over the `__API_BASE__` and
`__ATS_DOMAIN__` placeholders at build time
(`.github/workflows/testflight.yml`); locally, over the air, and on the server
they come from `TASKMASTER_PUBLIC_BASE` in `~/.config/taskmaster/env`, outside
the tree. An unstamped checkout has no default server at all and says so —
Settings offers the field, the widget says "Server not configured" — which is
what a browser opened on `www/index.html` uses with `?server=`.

**Ruled out:** `tailscale serve` HTTPS (needs sudo the session does not have —
`sudo -n -l` lists only systemctl/iptables/docker/nginx; it can be added later
in one command, see server/README.md); reusing the `:9970` dashboards vhost (a
root-owned nginx edit for no benefit); the household's public DDNS name (would
need a router port-forward and real auth for a single-user app).

## D5 — Same shell as the other apps

Capacitor 8, bundled mode, `www/index.html` is the whole client, no framework,
no build step, no external requests. Copied from `~/projects/orderconfirm-ios`
and `~/projects/carpool`, minus push (nothing here needs to reach a closed app —
Pushover already does the reminders). TestFlight via the same
`.github/workflows/testflight.yml` shape and the same four Apple secrets.
**Dispatch-only**, never on push: macOS minutes are billed 10x and August ran
out on redundant builds.

App id `org.rightwaytrey.taskmaster`, display name **TaskMaster** (what the user
calls it), repo folder `~/projects/todoapp`.

## D6 — Optimistic UI with an offline queue

Every write applies to the local model first and is queued; a drain loop sends
queued operations in order. A completed task strikes out instantly with a
5-second Undo; an added task appears instantly with a temporary id that is
rewritten when the server answers. The server list wins on every refresh, with
unsent operations re-applied on top so the screen never flickers backwards.
Refresh happens on launch, on foreground, every 30 s while visible, and after
every write. That is the whole answer to "sync lag": there is nothing to sync.

## D7 — Home-screen widget: it fetches the API itself

*Added 2026-09-04, after D1–D6 shipped.*

A native WidgetKit extension, `ios/App/TaskMasterWidget/`, showing what the
Scriptable widget shows: a "Today" header with a count, overdue rows first in
red, then due-today, "+N more" when it does not fit, "Nothing due 🎉" when it is
empty, and an "updated Xm ago" footer. Small/medium/large hold 3/6/12 rows.

**It calls `GET /api/tasks` itself, over the tailnet, exactly like the app.** It
does not read a file the app left behind, because it cannot: an extension is a
separate bundle with a separate container, and the only way to share one is an
**App Group — which is an entitlement**. This app has no entitlements, and that
is not an accident: it is what lets CI archive UNSIGNED and dodge the Apple
Development certificate cap (the comment at the bottom of
`ios/App/App/Info.plist`, and the "Archive (unsigned)" step in the workflow).
Adding an App Group would mean archiving signed, the way `carpool` and
`prayerlist` have to. Not worth it for v1.

Two consequences, both accepted:

- **ATS is per bundle.** The app's scoped exception for the tailnet domain does
  not cover the extension, so `TaskMasterWidget/Info.plist` carries its own
  copy. Same scoping rules as D4 — a domain, never an IP.
- **The server URL is a build-time value, not a Settings one.** The extension
  reads it out of its own `Info.plist` (`TaskMasterAPIBase`, stamped from the
  same `TASKMASTER_API_BASE` secret as `API_DEFAULT` in `www/index.html`), so it
  needs no entitlement to get at it — but Settings → server URL still does not
  move the widget, because reading *that* is what would need the App Group.
  There is one user and one server, so this has never been two values. Unstamped
  it says "Server not configured" and never fetches.

**Refresh.** The timeline asks for `.after(now + 15 min)` — advisory, iOS
throttles it, and it is the same hint the Scriptable widget's
`refreshAfterDate` gave. On top of that the app calls
`WidgetCenter.shared.reloadAllTimelines()` from `sceneDidEnterBackground` in
`SceneDelegate.swift`, so completing a task and swiping home updates the widget
at once rather than up to 15 minutes later. It is the **Scene** delegate because
the app is scene-based (`UIApplicationSceneManifest`); the
`applicationDidEnterBackground` stub the Capacitor template leaves in
`AppDelegate.swift` is never called and a reload put there would be inert.

**On failure** the widget re-renders the last response body that parsed, kept in
the extension's own `UserDefaults.standard` (its own container, no entitlement
needed), and the "updated Xm ago" footer is what admits the data is old. With no
cache at all it says "Can't reach the server". The raw body is what is cached, not
finished rows, so overdue/today and the clock labels are recomputed for the
current time even when the data is hours old.

**Dates** use the D3 rule and the same string comparison as `groupOf()` in
`www/index.html`: compare local `"YYYY-MM-DD"` strings, never `Date` instants. A
date-only due today is not overdue until tomorrow; a clocked one is overdue a
minute after its time.

**Bundle id** `org.rightwaytrey.taskmaster.widget`. It needs its own App ID in
the portal — see SHIP.md. **Ruled out:** shipping the target as a committed
pbxproj only (there is no Xcode on this box to repair it with, so
`scripts/add_widget_target.rb` regenerates it idempotently); replacing the
Scriptable widget's data feed (it is fed by `pa retag` through the Taskwarrior
hooks and is nobody's dependency here — D1).

**Future work**, in the order it would be worth doing: an App Group so the app
can hand the widget its cached list and its Settings server URL — one
entitlement, one signed-archive workflow change, and the widget stops needing
the network at all; then a deep link so a row opens `#/task/<uuid>` instead of
just launching the app.


## D8 — One canonical order, shared by the app and the widget

*Added 2026-09-04.* The user tapped the widget and found the app listing the
same tasks in a different order. There is now exactly one ordering rule, spelled
out in docs/api.md under "Canonical order", and both `www/index.html` and
`ios/App/TaskMasterWidget/TaskMasterWidget.swift` implement it verbatim: group
(overdue, today, upcoming, no date), then due date, then clocked time with
date-only last, then priority H > M > L > none, then uuid so the order is total.
A tap on the widget opens the Tasks tab at the top, so the first rows on the
home screen are the first rows on the phone.

## D9 — Filters are chips, not a language

*Added 2026-09-04.* "How can I filter what's shown?" The answer is a single row
of chips above the list: **All**, then one chip per project in use, then the
`claude` and `alert` tags. One tap narrows, the chip shows the count, the
choice persists, and the group headers keep working inside it. No query
grammar, no saved filters, nothing premium — the things that made Taskchamp's
filters confusing (design.md, top). `pa` — and anything else writing to the same
Taskwarrior — can stage a task tagged `button`; the app renders it as a distinct
confirm-first action row rather than an ordinary tappable circle, because
completing such a task triggers something downstream, and a plain checkbox got
tapped by accident on 2026-09-04. The `button` tag is not offered as a filter
chip: it marks how a row behaves, not a slice of the list worth filtering to.

## D10 — Complete from the widget

*Added 2026-09-04.* The row's circle on the widget is an iOS 17 interactive
button backed by an App Intent that POSTs `/api/tasks/{uuid}/done` straight to
the API and lets WidgetKit redraw. The widget target's deployment floor moves to
iOS 17 for this (the app stays at 15); the user's phone is well past 17.
Nothing changes on the server: it is the same call the app makes.

## D11 — Web changes ship over the air, not through Xcode

*Added 2026-09-04, after "please do not burn my GitHub Actions minutes".* Every
store build is ~30 billed macOS minutes and most changes to this app are to one
HTML file. So the shell gains the same live-update plugin TransitNav uses
(`@capgo/capacitor-updater`, self-hosted), the API serves the bundle manifest
and zips from the tailnet, and `scripts/publish_bundle.py` turns `www/` into a
bundle the installed app picks up at its next launch. A store build is needed
only when something native changes: a plugin, Info.plist, the widget, the
updater's own config. TransitNav's `docs/SHIPPING_WEB.md` is the model.

**Built the same day.** `@capgo/capacitor-updater` 8.51.15 and `@capacitor/app`
8.1.1 are in `package.json`; the config block is `plugins.CapacitorUpdater` in
`capacitor.config.ts` (`autoUpdate: 'onLaunch'`, our own `updateUrl`, stats and
channel URLs set to `''` so nothing is reported to Capgo, `appReadyTimeout`
10 s, `resetWhenUpdate`); the server side is `server/app/routers/app_update.py`
serving `POST /api/app/update` and `GET /api/app/bundles/…` out of
`server/bundles/`; `scripts/publish_bundle.py` builds the zip and
`scripts/ship_web.sh` publishes and then verifies it the way the phone will.
The exact wire protocol is in docs/api.md, cited to plugin source lines — it is
undocumented upstream and worth re-reading after any plugin upgrade.

Three things that were not obvious and cost a phone launch each if got wrong:

- **A non-offer must carry `kind`.** The plugin only routes a response to its
  no-update handler when `error` or `kind` is non-empty; a bare `{"message": …}`
  falls through to an empty download URL and logs a failure once per launch on a
  healthy app. An empty bundles directory answers `up_to_date`, not `failed`,
  because empty is this server's normal resting state.
- **The token gate cannot cover these two paths.** The plugin has no way to send
  an `Authorization` header (`CapgoUpdater.swift:207`), so `TASKMASTER_TOKEN`
  would silently break live updates. `app/middleware.py` exempts them from the
  token and only the token; the tailnet allowlist still applies, and what is
  exposed is a zip of the same `index.html` that is already in the binary.
- **`notifyAppReady()` is load-bearing.** A bundle that does not reach it within
  `appReadyTimeout` is rolled back — silently — so `publish_bundle.py` refuses to
  package a client that does not contain the call, and refuses one missing the
  `__BUNDLE__` placeholder that tells the Settings screen which bundle it is on.
- **A bundle carries the default server URL too.** `www/index.html` ships with
  `__API_BASE__` unstamped (D4), so `publish_bundle.py` stamps it into the copy
  from `TASKMASTER_PUBLIC_BASE` — `~/.config/taskmaster/env`, mode 600, outside
  the repo, and the same file the systemd unit reads. It refuses to publish
  without it: an unstamped bundle would replace a working client with one that
  has no server, and Settings would be the only way back. The server's
  `bundle_public_base` reads the same file, and has no default in code — with
  it unset, every check is answered "no bundle published" and a warning goes to
  the journal.

**A bundle is inert until a store build carrying the plugin is on the phone**,
because nothing on the installed shell is asking yet. And a bundle must never
depend on a native change an installed shell lacks — that is what `--min-native`
is for; the API answers `"needs native 1.0.9"` and withholds it. `server/bundles/`
is therefore left **empty** until the planner says otherwise.

## D12 — Feedback before the wire

*Added 2026-09-04, from "Same thing when unchecking on the done tab, little
feedback on clicks goes a long way." The "same thing" is the widget (D10), which
shows a check mark on tap, holds the row for a grace period, and only then
removes it.*

Both tabs now work that way, from one state machine — `arm()` / `cancelArm()` /
`commitArm()` in `www/index.html`:

```
                tap the circle
   resting ─────────────────────► ARMED  (looks completed / reopened;
      ▲                            │ │    NOTHING queued, nothing sent)
      │        tap again           │ │
      └────────────────────────────┘ │ 1.2 s
                                     ▼
                                 COLLAPSING (250 ms) — the op is queued and the
                                 5 s Undo toast goes up
```

**The op is queued at the end of the grace, not at the tap.** That is the
decision, not an implementation detail: a wrong tap caught inside 1.2 s never
reaches the server at all. Firing at the tap and cancelling by queueing the
opposite would put a `done`/`undone` pair on the wire for a mistake corrected in
under a second, and each of those runs the Taskwarrior hooks (D1) — `pa retag`,
the Scriptable widget's feed, `pa-pushnow`. Nothing about the queue changed after
the grace: the Undo toast still tears the op up if it is still queued and still
asks the server for the opposite if it has already gone.

**Un-completing had no feedback at all** before this, which is what the user
actually hit. It is now the exact mirror: the check empties, the strike lifts,
the row holds, a second tap cancels, and the toast is "Moved back to Tasks ·
Undo" whose Undo re-completes.

**A `button` row keeps its old path** and completes on the spot. It has just
answered a confirm dialog naming the task — a stronger cancel than a second tap
— and it has no circle to tap again, so a grace there would be 1.2 s in which
nothing could be done (D9).

**`prefers-reduced-motion` drops the animations and keeps the timings.** The
bounce and the collapse are decoration on a state the app is in anyway; the
grace, the cancel and the 5 s Undo are the behaviour. Someone who asked for less
movement did not ask to lose the chance to take a tap back.

**Ruled out:** a longer grace instead of the Undo toast (the toast survives the
row leaving the screen, and reaches the case where the phone was offline and the
op is still queued); an undo *stack*; and holding the render for the whole grace
without releasing it on a cancel — the next thing typed has to appear at once.

Client-only, one file: it ships as a bundle (D11), no native change.

## D13 — Categories are Taskwarrior projects, picked from a list

*Added 2026-09-04, from "Would like categories on tasks, choose from list."*

A **category is Taskwarrior's `project`**. The field stays `project` everywhere
it is a field — the API (docs/api.md), the model, the `p:` filter chip values,
the widget's Swift — and the word changes only at the glass, because "category"
is what the user calls it and what it is: one name, chosen from a list, saying
where a task belongs. Renaming the field would have meant a migration in `pa`,
the digest, the `on-modify` hooks and the Scriptable widget's feed for a word
(D1).

**Why not a new field:** tags already exist and are a *set*; a category is
exactly one, which is precisely what `project` is. Two overlapping "which bucket"
fields is the thing that made Taskchamp's filters confusing (top of this file).

**One list, one function.** `categoryList()` in `www/index.html` feeds both
places that offer it — the quick-add picker and the detail sheet — so the two
can never present different sets. Its order is `/api/meta`'s: the five `pa`
categories first, in `pa`'s order (personal, work, claude, fun, inbox), then
every other one the server has seen, then anything a task on *this* phone is
using that the server has not heard of yet, which is what an offline-added task
with a brand new category is until it lands. Then "New category…", which prompts
for a name, validates it against the server's own rule verbatim
(`^[A-Za-z0-9_.-]{1,40}$`, `clean_project()` in `server/app/schemas.py`) and
lower-cases it, so `Work` typed on the phone and the `work` that `pa` writes are
one category and not two chips that look alike. A name that fails is refused
here with a toast rather than becoming a queued op the server drops with a 422
half a minute later.

**The quick-add choice is sticky**, persisted as `tm.qaCategory`. Capture is a
burst activity — three things for work, then two for the house — and re-choosing
per task would be the tax that stops the thing being used. Like the filter it is
a *preference*, not a cache, so "Clear local cache" deliberately leaves it alone.

**A category filter chip still wins over it** (D9): adding a task inside a filter
and having it vanish from the list you are looking at is indistinguishable from a
bug. So while a filter is on, the chip shows the filter's category and says so
underneath. Picking a *different* category in the picker then **moves the filter
with it**, because the alternative is a chip that says one thing while the task
goes somewhere else — the filter confusion this app exists to end. A tag filter
is untouched: it does not decide the category, so there is nothing to reconcile.

**Ruled out:** a free-text category field at capture time (typo-prone, and it
makes a new category by accident — which is exactly how a project list becomes
noise); more than one category per task (that is what tags are); and putting the
picker behind the detail sheet only, which would have left the answer to "where
does this go?" one screen away from the moment of typing it.

Client-only: it ships as a bundle (D11), no native change. The widget shows every
category and is unaffected.
